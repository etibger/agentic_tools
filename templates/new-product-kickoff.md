# New-product kickoff — toolbox v0.2

Use with the completed `work-contract.md`. Start with discovery. Product implementation follows an agreed first-slice contract; exploratory code or live probes require an explicitly bounded scope within the user's authority.

## Execute

Before discovery/investigation, show the shared contract's project structure, initial team, provisional execution team, proposed models/effort and investigation bounds.

1. Establish the problem, user and success observation. Ask only questions that materially change direction. Separate known facts, assumptions and optional ambition. Do not turn every idea into a committed requirement.
2. Inspect relevant existing tools, interfaces and environment prerequisites. Choose a bounded feasibility probe for the assumption most likely to invalidate the product. State allowed mutations, outputs, recovery and what evidence would reject the approach. Resolve missing authority before that dependent action.
3. Execute only authorized probes and report observed results. A simulator qualifies its simulated contract; a health endpoint does not prove the consumer's real user journey. If prerequisites are unavailable, record the limit and a decision with concrete alternatives rather than build a large supporting system by default.
4. Present the Detailed Investigation and a continue/change/defer/stop recommendation grounded in need, feasibility and remaining cost. Include the proposed solution/alternatives, test strategy, ordered plan, team/model settings, resources, estimates and stop conditions. Obtain the user's Concept Approval for its exact first-release revision before implementation, unless explicitly waived for this task. Record acceptance, exclusions, environment, assurance, delivery and receiving owner. Confirm the actual team; preserve settled decisions and do not infer commitment from silence.
5. Hand each accepted delivery increment to the feature-change workflow using the same work contract and accepted baseline. Probe the most constraining capacity boundary early. Keep one product backlog and maintenance owner; feature projects can close independently.
6. Deliver and demonstrate the first usable release at its agreed boundary, with actual integration evidence, setup/recovery, limitations and ongoing ownership. Compare observations with the original assumptions and select proportionate follow-up learning.

Discovery can end with a justified decision to stop or defer. No automatic repository creation, remote setup, installation, external publication or permanent multi-agent crew follows from this template.
