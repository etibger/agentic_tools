# Future improvements

This register records a bounded Tide & Tile coordination audit on 23 October 2026. The proposals are **future workflow experiments**, with suggested owners and acceptance criteria. This documentation change does not implement them in the reusable templates, renderer or automation.

The objective is shorter waits between ready prerequisites and useful work. Keeping every agent busy is not a useful target: waiting for a frozen candidate or exclusive native resources can be correct.

## Prioritized experiment register

Targets below are proposed trial criteria, not achieved service levels or promised gains.

| Priority and proposal | Suggested owner and trigger | Trial acceptance and principal risk |
| --- | --- | --- |
| **P0: visible role freshness.** Separate active, waiting, available and completed assignment states; distinguish dispatched from observed-active work. Show each role's observation time/basis, candidate and wait reason. Keep runtime-audit, source-write and fetch ages separate. | Dashboard owner with Coordinator observations; next authorized schema/renderer task. | Fresh HTTP plus old observations must remain visibly stale. Ten meaningful transitions should reflect consumed facts within 60s, with misses recorded. Risk: polling overhead and false precision; use event updates with periodic reconciliation, and label receipt times when actual audit times are missing. |
| **P1: earlier compiler feedback.** Run cheap normal builds and affected safe tests before the combined frozen-candidate acceptance; allow read-only review in parallel. Join independent source assessments and actual check evidence in one acceptance report, preserving independent initials and actual exchange. Reserve separate pre-execution review for risky native mutations. | Coordinator and Verification; next candidate inside the approved DI and safety boundary. | Across three candidates, record time to first compiler feedback and repeated source-only gates before it; target no redundant pre-build acceptance gate. Risk: tests can have native effects; classify commands first, keep one output owner and require the existing safety approval/review before risky actions. DI approval still precedes dependent stages. |
| **P1: finite conditional releases.** Once command prerequisites are satisfied, authorize one named build and, only on success and unchanged identity, one bounded hidden test. Retain separate outputs; stop on failure, drift or unexpected effects. Where already authorized, combine exact-scope staging, full-index review and conditional commit, preserving separate source/docs commits and independent tree verification. | Coordinator and Verification; known commands inside an approved safety boundary. | Remove at least one round trip per eligible build/test sequence. Across three candidates, target median build-end-to-test-start below 30s when no dependency wait exists. Risk: accidental authority expansion; specify candidate, commands, attempts, timeout, effects, stop/release conditions. Git/execution authority and changed safety boundaries remain explicit. |
| **P1: event handoffs and a small native queue.** Consume a completion, record disposition and dispatch the next ready assignment together. Use a mechanism that starts completed agents. Track candidate, scope, prerequisite, owner and ready/acquired/released times for the shared lane. Reconcile overdue leases against actual jobs before takeover. | Coordinator; every completion or native-resource release. | Every consumed completion has a next action or named dependency; no duplicate native owners; investigate ready items waiting over two minutes without a reason. Measure consumption-to-dispatch separately from queue wait. Risk: duplicate events; deduplicate by assignment/candidate and check execution before retrying. |
| **P1: focus independent rechecks on the affected contract.** Dispatch the same complete candidate identity, exact delta, prior failure and check obligations to all required roles together. Each independently justifies evidence reuse and assesses changed dependencies/integration points. Exchange conclusions after independent initials. | Coordinator, Reviewer, Devil's Advocate and Verification; correction after a failed freeze. | Every reused result cites its prior scope and unchanged prerequisites; every changed obligation gets rechecked. Track setup time, reopened obligations and escaped defects. Risk: small text changes can have broad effects; reviewers may expand scope. Do not repeat unchanged design review without a concrete reason. |
| **P2: bounded receipts and harness preflight.** Keep canonical manifests/logs immutable; summarize candidate, delta, result, limits, findings and next action with references. Keep history outside the current dashboard projection. Validate required pin keys, documentation inclusion and artifact paths before acquiring the lane. | Verification, Coordinator and Dashboard owner; next authorized evidence/harness task. | No receipt-shape failure across three candidates; all gate evidence remains resolvable. Aim for handoff summaries under 2 KB, measuring preparation time before setting a dashboard budget. Risk: indirection hides evidence; require primary-evidence reading and relevant before/after identity checks. Retain failed reports. |

These proposals address observed handoff structure and display defects. The hypotheses are that fewer releases and repeated context packets will reduce latency, and that canonical evidence will reduce preparation cost. Neither causal claim is measured yet. Read-only assessment and documentation preparation can overlap where inputs/resources are isolated; native commands retain one owner. A general scheduler is unnecessary for the first trial.

## Next trial and existing mitigations

The project already applied a local V8 dashboard correction for audit/receipt freshness, dependency visibility and dispatched counts. Its retained repair receipt reports HTTP/schema/renderer checks; browser visual verification was not performed by the Dashboard owner. The Coordinator also began combined conditional verification/preflight handoffs and exact-index staging/commit assignments. These are local mitigations, with effectiveness unmeasured; this register does not claim reusable adoption.

1. Select at most three experiments: role freshness, finite build/test release and completion/queue records. Register fields and eligible commands before the next authorized workflow revision.
2. Observe three comparable frozen-candidate cycles. Record freeze, source-gate-ready, queue-ready, acquired, command start/end, report-ready, consumed, dispatched and observed-active times where available. Keep missing values unknown; classify review, resource, finding, approval, dispatch and unknown waits.
3. Exercise stale-role/fresh-fetch, completed-agent dispatch, duplicate completion, command failure and identity drift. Require correct waits/stops and no invented passes.
4. Compare median/maximum waits, round trips, harness errors, stale-state corrections, duplicate executions and escaped/reopened findings. Retain, revise or reject experiments in the retrospective and track selected actions. The small historical sample cannot establish causal speedup.

Preserve GPT-6.1 Sol/high launch settings, one product writer, exclusive native outputs, incremental reviewable commits, independent same-candidate initials and actual exchanges, separate documentation checkpoints and independent tree verification. Preserve no-foreign-window actions, approval for changed safety boundaries, the real 99-count campaign and separate physical-input evidence. No timing target waives a blocked native or safety check.
