# Worked examples

These are routing and contract walkthroughs, not newly executed projects. Finance uses a hypothetical defect. The native game and connector examples adapt existing project concerns. Navigation and copy-mode examples draw on historical Herdr personal-project DIs and retrospectives reviewed on 24 October 2026. Source-review readiness, reported local acceptance and independently rerun evidence remain distinct; this review did not rerun those projects or inspect every retained log.

The examples are independently written and omit private data, internal-service links, raw records and source archives. Names describe scenarios; the workflow/profile selections below are proposed pilot choices, not retroactive changes to any project's approved process.

## Finance: correct a derived report

**Scenario:** a synthetic pair of transactions is counted twice in a monthly category report. This is an invented defect used to exercise the workflow; it is not a finding about a real finance repository.

**Contract:** correct aggregation while preserving accepted transaction records, unrelated reports and private data. Delivery is a locally reviewable candidate. No ledger rewrite, import, external publication or installation is implied. Discover the actual project's native check recipes before execution.

**Path:** reproduce the double count with synthetic inputs → trace report aggregation and direct consumers → agree the narrow repair within the user's instruction → fix and run affected checks → independent execution/source assessment → compare report output and preserved inputs. The first feedback should be the minimal report observation, not a dashboard setup.

**Exit:** demonstrated correction, relevant regression evidence, final source identity and accurately scoped documentation. If the expected categorization itself is undecided, resolve that behavior and route the change as a feature. If the repair must mutate accepted records, reassess effects, recovery and authority before proceeding.

## Native tiling game: add save and restore

**Scenario:** an existing game needs a coherent save/restore journey while sharing a desktop window manager with the user. This adapts an active-project acceptance problem; it does not authorize changes to that project.

**Contract:** save the observed state, restore with fresh window identities, observe the intended result and clean up owned resources. Record display, scale, capacity, target context and allowed effects. Keep physical-keyboard qualification and any already committed broad playthrough matrix as separate required claims.

**Path:** agree the behavior → qualify a small actual constructor/restore/cleanup slice and the constraining capacity boundary → implement useful increments → assess actual geometry and identity on one coherent candidate → execute the remaining committed acceptance. A display change invalidates affected geometry/capacity assumptions; source-only and model evidence retain their narrower scope.

**Coordination:** one executor owns the shared desktop. Preparation workers can design cases or assess actual results; their work does not count as actual playthroughs. The milestone graph names each wait. Independent documentation preparation must not block unrelated source work. Fact packets contain no peer conclusions, including in referenced helpers.

**Exit:** agreed real journeys and mandatory counts completed, physical-input obligations resolved at their agreed boundary, recovery demonstrated and selected delivery outputs verified. Source approval and large pure-test counts cannot close missing native evidence.

## Acquisition connector: discover a first usable product

**Scenario:** a new service must connect a consumer application to an external catalogue/provider. Existing connector documentation distinguishes offline contract simulation from a real consumer installation.

**Contract:** define the user's smallest acquisition journey, the consumer version/interface, provider behavior, supported content and first-release environment. Separate search, validation, acquisition response and the consumer's actual download responsibility. Set an exploration limit and identify required access.

**Path:** inspect the consumer contract → run a bounded provider feasibility probe when authorized → agree continue/change/stop → deliver one search-to-acquisition slice through the feature workflow → exercise the actual consumer at the selected delivery boundary. Add breadth only after the representative path works.

**False positive:** an offline simulator or green health response cannot establish that the user's installed consumer accepts the result and completes its part of the journey. A pinned reference consumer and an unverified moving image tag are different environments.

**Exit:** an observed first usable journey, setup/recovery, limitations and maintenance ownership. Offline-only acceptance is possible only if that narrower boundary is explicitly agreed; do not describe it as an observed production integration.

## Navigation popup configuration: feature delivery plus a narrow repair

**Historical basis:** the popup retrospective reports accepted local manual-review delivery after frozen milestones, independent assessment, interaction checks and documentation verification. At its cutoff the source was uncommitted and the product uninstalled. This is a reported historical result, not a newly verified release claim.

**Contract:** configure displayed information while preserving search, logical destinations, input behavior, compatibility and shared protocol boundaries. The first vertical slice joins prepared content, rendered cells and destination activation; a parser-only slice cannot establish the user outcome.

**Repair branch:** malformed settings were rejected but their diagnostic omitted the owning configuration path. Green suites did not satisfy that acceptance clause. Treat the narrow correction as a bug-fix assignment inside the feature: reproduce exact diagnostic context → repair → refreeze → independently recheck changed behavior and directly affected consumers. Continue the existing feature contract afterward.

**Coordination lesson:** source reviews can finish while actual interaction verification continues. Assign useful read-only harness review where appropriate, preserve initial independence and qualify isolated documentation work. Distinguish product defects, mistaken fixtures and cleanup failures. Optional usage telemetry does not become product acceptance.

**Exit:** the agreed local candidate and its actual interaction evidence. Recorded platform exceptions and unrun environments remain visible. A historical plan's approval wording is not a live status source.

## Contextual navigation entries: bounded enhancement on an accepted base

**Historical basis:** the reviewed context DI was a source-only proposal at its publication cutoff, with implementation/testing unrun and design approval pending. Later source baselines may contain newer behavior; this walkthrough does not infer current project status from the old proposal.

**Contract:** show identity/title and directory together while preserving explicit configured layouts, semantic search, endpoint-qualified targets and existing wire contracts. Information absent from the available snapshot is an explicit limitation rather than an invitation to expand runtime transport.

**Path:** pin the existing configurable-popup baseline → agree unset defaults and compatibility/fallback behavior → compose one real entry and exercise its destination → verify narrow/Unicode/missing-data and lifecycle boundaries → deliver the agreed enhancement. Reuse accepted configuration behavior with an impact rationale.

**Decision:** changing a default is a feature decision even if motivated by a confusing display. A publication-ready design is not implementation approval or executed validation. Keep design decisions and tool/environment readiness separate; do not carry an old platform exception into this new scope automatically.

**Exit:** agreed default and explicit-layout compatibility demonstrated on the named candidate, with actual evidence and unrun limits. Until execution exists, the result remains a proposed plan.

## Elastic popup width: classify by contract and verify coupled behavior

**Historical basis:** the reviewed elastic-width DI was a revised source-only proposal. It specified geometry, viewport and validation obligations; no implementation or execution result was established by that page.

**Contract:** adapt width to drawn content while preserving compact behavior, bounded geometry, selection, scrolling and destination input. Hidden, filtered and offscreen content must not force growth. State the intended sizing policy before calling the report a bug; a changed sizing contract follows the feature workflow.

**Path:** observe baseline clipping → agree the policy → calibrate one long-content composed frame → change to short content in the same still-open overlay → inspect vacated cells, selection and recomputed hit targets → exercise resize, narrow/Unicode, scroll and reload boundaries. Use separate activation branches where accepting a target closes the overlay.

**False positives:** a helper returning the expected width does not prove visible cells or hit correctness. Reopening the overlay between long and short cases misses the lifecycle claim. A zero-origin buffer can hide centering errors. A narrow-only performance fixture cannot qualify newly wide behavior.

**Exit:** actual composed behavior and input outcomes, matched performance scope and independently assessed coverage. Environment exceptions require their own current decision. Publication and source review alone leave this exit unfulfilled.

## Copy-mode motions: follow a discovered contract across consumers

**Historical basis:** the copy-mode retrospective reports multiple reviewed candidates, regressions exposing earlier failures and a later personal installation. Manual terminal, Windows and remote-CI coverage remained limited; some original full-suite results were reported without separate retained logs. This review did not recreate those runs.

**Contract:** add character-find/repeat behavior while respecting generated text, committed events, modifiers, cancellation, terminal-cell boundaries and asynchronous acceptance/rejection. New capability discovery and compatibility are part of the feature boundary.

**Path:** characterize one useful motion → implement and assess → on a confirmed generated-input defect, inspect target and command consumers plus immediate queue/error guards → demonstrate failing-before/passing-after regressions where possible → qualify integrated behavior and the actual delivery boundary. Stop the consumer sweep when the implicated contract ends; do not audit unrelated keyboard systems without evidence.

**Coordination lesson:** broad green suites can miss an input representation. Reviewer agreement is not execution proof. Discover script runtimes and direct recipe prerequisites early, retaining missing evidence separately from unrun checks. Local acceptance, personal installation and upstream eligibility remain distinct decisions.

**Exit:** observed motions and ordering behavior at the agreed scope, source/build provenance, maintained documentation and honest remaining limits. A proposed retrospective action is not an implemented safeguard or a demonstrated speedup.

## Walkthrough results and next pilot

The seven cases fit three entry points. None requires a project-specific fourth workflow: diagnostic repairs remain bounded assignments within features, and product discovery hands off delivery increments. Assurance follows effects; integrations follow explicit project needs. The examples also reveal shared obligations worth retaining: direct-consumer reasoning, real integration evidence, decision/candidate lineage, resource ownership and truthful delivery states.

These are design walkthrough results, not evidence of improved execution speed. The first real pilot should be a user-selected bounded bug fix with a known expected result and a usable native environment. Complete its work contract before implementation, retain the first meaningful feedback and handoff observations, then assess which fields and steps helped. No finance defect, game migration, connector deployment or Herdr task is started by this page.
